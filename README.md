# 奶茶饮品店 · 原料库存与配方出单

奶茶饮品店的原料库存、配方出单、会员积分与出杯退款管理。后端 Spring Boot + JPA，前端 Vue 3 + Element Plus（焦糖主题、顶部标签页导航）。

## 启停

```bash
sh start.sh     # 启动（后端 + 前端 + MySQL）
sh stop.sh      # 停止
```

## 模块

- 原料库存：茶底 / 奶 / 小料 / 糖浆 的库存与启用停用
- 配方出单：勾选小料 + 右侧抽屉填份数生成配方（小料用量用 `@ElementCollection Map` 承载）；每杯另固定消耗茶底 10（`Dict.BASE_TEA_PER_CUP`）
- 会员：手机号对“有效”会员唯一，消费累加积分并按阈值升级（银卡 ≥ 500，金卡 ≥ 2000）
- 出杯记录：按配方明细汇总金额，仅「已出杯」可退款并回退积分

## 配方售价金额口径（全系统一致）

- **统一精度**：配方售价与订单金额一律按「分」精度（`DECIMAL(10,2)`，两位小数）落库与返回；服务端 `Money` 统一校验/收口，Jackson 以普通数字（非科学计数法）序列化。列表、编辑表单、出杯选择器、订单预览、订单列表对同一配方只显示同一个 `price`。
- **稳定校验提示**：售价空 / 0 / 负数 / 超过两位小数 / 超过上限（`Dict.RECIPE_MAX_PRICE=99999999.99`）都在服务端最新数据上校验并返回固定中文提示；系统**绝不静默四舍五入**，三位小数输入直接拒绝。边界 0.01 与 99999999.99 可正常保存为 `"0.01"` / `"99999999.99"`。
- **旧数据显式降级**：`recipe.price`（规范列，可空）+ `recipe.price_raw DECIMAL(12,4)`（历史原值，仅回显）。历史遗留的多位小数（如 10.1250）或空价格，读取时 `price=null` 并带 `priceStatus`（`legacy-multi-decimal` / `legacy-empty` / `legacy-invalid`）与 `priceNote` 修复指引：列表红色「待修复」标签、编辑表单留空并告警、出杯选择器禁用该配方，服务端预览/下单也拒绝计价（整单不落库，失败留痕）；在编辑表单人工确认规范价后恢复 `ok`，不做自动转换。
- **并发一致性**：`recipe.version` 乐观锁 + 保存行内最新版本校验，多页面交替编辑时过期提交稳定拒绝（前端保留用户输入、回填最新版本后可重试）；重复点击提交由前端保存锁 + 服务端唯一约束/版本双重兜底；列表与预览的只读请求带序号，过期响应直接丢弃，快速连续操作后最终状态以最后一次响应为准。
- **验收脚本**：`bash accept_recipe_price.sh`（需 `sh start.sh --build` 重建以应用新 schema），覆盖边界金额、精度转换、旧数据回显与修复、重复/连续/交替操作最终状态、订单预览与落库金额计算。

## 会员档案合并与联系方式变更审计

- **标记与预览**：店员可在「会员 → 档案合并与审计」把重复会员标记为待合并，选择保留的主档；执行前可预览两边手机号、姓名、积分、等级、历史订单数，并按积分流水合计预演合并后积分。
- **冲突不静默覆盖**：执行前必须检查**手机号冲突**（组内同号、号码被组外有效会员占用、历史遗留重复号）与**积分来源冲突**（会员余额 ≠ 积分流水合计）。任一不通过，合并单进入「冲突待处理」并记录冲突类型与明细，店员处理（改手机号/补记流水）后在同一入口“重新检查”，通过后才合并。
- **合并结果**：历史订单整批改挂主档（逐笔登记 `member_merge_order`，撤销可逐笔挂回）；积分流水整批改挂主档并记 `origin_member_id` 与合并单（不复制、不新增，故不重复计算）；副档手机号有效绑定改指主档；副档转为「已合并」只读别名，原样保留手机号/姓名，并留合并原因、操作人、时间。查会员时按旧号/别名能解析并追溯到主档。
- **撤销合并**：仅「负责人」角色可发起；订单按迁移记录逐笔挂回，积分流水按来源整批挂回原档（主档自身及合并后新增流水不动），手机号绑定指回，主档/副档余额各自按流水合计重算——全程不重复计算积分；重复撤销由合并单状态与行锁稳定拒绝。
- **联系方式变更审计**：手机号或姓名必须经专门接口修改并填写原因，保留变更前后值、原因、生效时间、操作人（`member_contact_audit`）；同一手机号不能绑定两个有效会员（`member_phone_binding` 以手机号为主键，服务端 `SELECT … FOR UPDATE` 串行化并发改号/建档）。
- **并发与幂等**：合并单与会员行均加悲观写锁并配合 JPA `@Version` 乐观版本；重复合并、并发合并、并发改手机号、重复撤销都以锁点最新状态/版本校验，得到稳定结果；合并执行接口幂等（已合并重复调用直接返回结果）。
- **筛选与详情**：合并单支持「待处理 / 冲突待处理 / 已合并 / 已撤销」筛选；详情展示成员合并前后差异（手机号/姓名/积分/订单数）、订单归属迁移、双方当前档案与完整生命周期审计事件时间线。

## 出杯库存履约闭环

- **下单前预览**：出杯页按每个配方的茶底 + 小料汇总本单原料需求（多个配方、重复明细合并计算），页面展示预计扣减与不足/停用原料；预览仅为提示，提交时服务端在事务内对原料行加悲观写锁、以最新库存复核。
- **整单原子**：任一原料库存不足、已停用或配方引用失效，整单不落库（`cup_order` / 明细 / 库存 / 积分同事务回滚，无负库存、无半扣、积分不先行增加），仅在「出杯失败记录」表留存失败原因；同一原料被两笔出杯并发争用时由行锁串行化，不可能两单都成功。
- **扣减快照**：出杯成功时逐原料保存 `cup_order_stock_snapshot`（原料 id、当时名称/单位、实际用量），之后配方被编辑也不改变历史消耗。
- **退款回补**：仅「已出杯」订单可退款且只退一次；严格按该订单快照精确回补原料（登记 `refund_qty`）并回退原积分，重复点击/并发退款由订单行锁与状态判定稳定拒绝。历史无快照的旧订单仍可退款，但只回退积分、不凭空回补库存。
